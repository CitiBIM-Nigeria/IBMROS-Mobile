# IBMROS — Physical QR → Product Deep-Link Feature
## Production Implementation Roadmap

> Status: **Plan only. No code written.** Execute phase by phase.
> Spans two repos: **`ros-pipeline`** (data/QR generation + link hosting) and
> **`IBMROS Mobile`** (Unity app: scan, deep-link, product detail).
> Author: architecture pass, 2026-07-18.

---

## Context

A shopper standing in front of a physical IKEA product should be able to scan a
QR code and land on that exact product inside the IBMROS Unity app — to preview
it, save it, or place it in an open AR room.

**Agreed architecture (fixed):**
- Each product gets a unique QR code containing an **HTTPS deep link** (an id, not product data).
- Scanning with the **native phone camera** opens the app if installed
  (iOS Universal Links / Android App Links), else redirects to the store.
- The app also ships a **built-in QR scanner**.
- A scan opens a **Product Detail screen** — it never auto-creates a room or
  auto-places furniture. Actions: Preview, Save for Later, Add to Current Room.

**Two facts from the codebase that shape everything below:**
1. **There is no backend HTTP API.** Unity talks *directly* to DynamoDB via the
   AWS SDK using Cognito **guest** credentials (guest-first app, usable without
   login). So deep-link resolution is a **client-side GSI query**, not a new endpoint.
2. **The `canonical-index` GSI already exists** (`group_canonical` → `merchant_id`),
   built for cross-region identity. It is exactly the index a deep link needs.
   The Unity client does **not** use it yet.

## The core design decisions (decided here, rationale inline)

### D1 — What the QR encodes
`https://<LINK_DOMAIN>/p/<canonical_id>`

- `<canonical_id>` = the product's **`canonical_product_id`** (worldwide IKEA
  article, region-independent; `ikea_pipeline.py:839`). Chosen over the per-region
  slug `product_id` because: it is stable, identical across GB/US/DE/FR, and it is
  the number IKEA prints on the shelf tag — so an operator matches physical↔label
  deterministically.
- The app extracts `<canonical_id>`, forms `group_canonical = "ikea#<canonical_id>"`,
  and resolves it via the **`canonical-index` GSI** → `product_id` → full product.

### D2 — No web application; static hosting only
The "app-not-installed" fallback + the OS domain-verification files are served as
**static objects from S3 behind a CloudFront distribution on `<LINK_DOMAIN>`**:
- `/.well-known/apple-app-site-association` (iOS Universal Links)
- `/.well-known/assetlinks.json` (Android App Links)
- `/p/*` → one static redirect page (platform-detect → App Store / Play Store),
  routed by a **CloudFront Function** (viewer-request URL rewrite). No server, no Lambda origin.

### D3 — `qr_url` is free; the QR image is a separate, low-priority artifact
- `qr_url` (the deep link string) is a pure function of `canonical_product_id`, so
  it is **set inline during scrape** — no job needed. Every new product gets it for free.
- The **QR image** (SVG in S3) exists *only* to be printed onto physical labels.
  The app never displays it. So it is generated by a **ride-along enrichment pass /
  backfill job**, exactly like `run_bg_backfill`.

### D4 — Ship a **lightweight, local-first Saved Items** feature — worth it
**Verdict: build it.** Justification: the scan happens *in the store*, where the
user is physically **not** in the room they'd furnish. Immediate placement is
impossible there, so "Save for Later" is the *natural primary action* of an
in-store scan. Without it, a scan has no satisfying outcome (Preview only) and the
in-store funnel dead-ends.
**Implementation: local-first** (device JSON/PlayerPrefs list of product ids +
cached minimal metadata) — **no new backend, no auth requirement** (works for
guests, matches the guest-first model, offline-capable, ships fast). A backend
sync table is a deferred future option (see Phase 8), not v1.

### D5 — Deep link lands on a **standalone** Product Detail screen
Today the only product detail UI (`ItemDetailSheetController`) lives **inside the
Room scene** and is opened by `RoomUIManager`. A deep link can arrive on the home
screen (`Main.unity`) with no room open. So we add a **standalone UI Toolkit
Product Detail screen** reachable from the home context via `ScreenNavigator`,
reusing the existing rendering logic. "Add to Current Room" is enabled only when a
Room session is active; otherwise the screen offers Save for Later + "Open a room
to place this" (no silent room creation).

### D6 — Security: no signed/tokenized links needed
The link carries a **public catalog id** to **read-only, guest-accessible** data.
There is no write path, no PII, no auth escalation reachable through the link.
Signing would add key-management burden for zero security gain. Instead: **validate
id format**, **validate the id resolves** (unknown id → friendly "not found"), and
lock down the hosting bucket/paths. (Details in the Security section.)

## Data Model Changes

### `ros-products` (DynamoDB) — two new optional attributes
| Attribute | Type | Meaning | Written by |
|---|---|---|---|
| `qr_url` | S | the deep link `https://<LINK_DOMAIN>/p/<canonical_id>` | scrape (inline) + backfill |
| `qr_image_url` | S | CloudFront URL of the QR SVG in S3 | QR image job / backfill |
| `qr_generated_at` | S (opt) | ISO timestamp of last QR image render | QR image job |

- No new table for QR. No key/GSI change *required*. (Optional: add `qr_url` to
  `canonical-index` `NonKeyAttributes` if we ever want the resolver to read it from
  the projection — not needed for v1.)
- Persisted via the existing schemaless path: add the keys to the optional-field
  loop in `DynamoWriter.write` (`ikea_pipeline.py:696-701`) and set them in the
  record dict (`~2295-2318`). `_attr()` serializes them automatically.

### Saved Items — **no DynamoDB in v1** (local-first, D4)
Device-local store only. Schema (local JSON):
`{ productId, canonicalId, name, thumbUrl, priceText, savedAt }[]`.
(Deferred backend option, Phase 8: table `ros-saved-items`, PK `user_id`
(Cognito sub), SK `product_id` — requires authenticated identity.)

### S3 asset additions
- QR image: `{merchant}/products/{slug}/qr.svg` (content-type `image/svg+xml`),
  via `AssetProcessor.upload_bytes` — same convention as every other asset.
- Link hosting objects (separate hosting prefix/bucket, see Phase 2).

## Infrastructure Changes (AWS)

| Resource | Change | Notes |
|---|---|---|
| **Domain** | **Acquire `<LINK_DOMAIN>`** (e.g. `l.ibmros.app`) | None exists today. Hard dependency for Universal/App Links. |
| **ACM cert** | Cert for `<LINK_DOMAIN>` in `us-east-1` | Required for CloudFront custom domain. |
| **S3** | New objects: `/.well-known/apple-app-site-association`, `/.well-known/assetlinks.json`, `/p/index.html` redirect page, plus per-product `qr.svg` | Reuse `ros-furniture-assets` under a `link/` prefix, or a small dedicated bucket. Bucket stays private (OAC). |
| **CloudFront** | **New distribution** aliased to `<LINK_DOMAIN>`, OAC to the hosting bucket; **CloudFront Function** (viewer-request) rewriting `/p/*` → `/p/index.html`; correct `Content-Type` for the extension-less AASA file | CloudFront is *not* code-managed in `setup_aws.py` (pre-existing, configured manually) — this is a manual/console or IaC addition. |
| **DynamoDB** | No table/GSI change required | `canonical-index` already exists (`setup_aws.py:184-218`). |
| **API / Lambda** | **None** | No API layer exists; resolution is client-side (D-fact 1). |
| **Cognito / IAM** | Verify the guest role can `Query` `canonical-index` | Guest role already reads `ros-products`; confirm the index is in the resource ARN/policy. |
| **iOS signing** | Set a **real bundle id + Apple Team ID** (currently the default template id) | AASA `appID` = `<TeamID>.<bundleId>`; must match. |
| **Android signing** | Capture the **release keystore SHA-256 fingerprint** | Goes into `assetlinks.json`; must match the shipped signing cert. |

### Phase 1 — Pipeline: QR data generation (repo `ros-pipeline`)
**Objective:** every product carries a `qr_url`; a QR SVG exists in S3 with its
`qr_image_url` on the record. New scrapes get it automatically; existing rows via backfill.
**Components:** ingestion pipeline, S3, DynamoDB, tools.
**Files likely to change:**
- `pipeline/ikea_pipeline.py`
  - Add region constant `LINK_BASE_URL` (from `<LINK_DOMAIN>`) in `configure_region()` (~L147-183).
  - New helpers: `qr_deep_link(canonical_id) -> str` and `render_qr_svg(url) -> bytes` (using **`segno`**, pure-Python, emits SVG/PNG, zero binary deps).
  - Record dict (~L2295-2318): set `"qr_url": qr_deep_link(canonical_product_id(...))`.
  - `DynamoWriter.write` optional-field loop (L696-701): append `"qr_url", "qr_image_url", "qr_generated_at"`.
  - Ride-along enrichment: `_scan_qr_jobs(db)` + `_qr_process_one(...)` + `run_qr_backfill(...)`, mirroring `_scan_bg_jobs`/`run_bg_backfill` (L2349-2446); invoked at end of a run unless `--no-qr`. Generates the SVG, uploads via `AssetProcessor.upload_bytes(svg, f"{s3_base}/qr.svg", "image/svg+xml")`, patches `qr_image_url` via `update_item`.
- `requirements.txt`: add `segno` (and `reportlab` only if PDF labels are wanted — see Phase 7).
- New `tools/backfill_qr.py` — clone of `tools/backfill_snapshots.py` structure
  (`find_missing`/`patch_row`/`run`/`main`): scans `ros-products` per `--region`
  for rows missing `qr_url`/`qr_image_url`, generates + uploads + `update_item`
  (surgical, never `put_item`), supports `--dry-run`/`--limit`. **No browser, no re-scrape.**
- Optional: extend `tools/verify_catalog.py` to assert `qr_url` present + `qr.svg` object exists.
**Dependencies:** Phase 0 (`<LINK_DOMAIN>` decided — but `qr_url` can be generated
with the chosen domain string even before hosting exists).
**Risks:** low. `canonical_product_id` is the family-min article, which may differ
from a specific colour variant's article — acceptable because QR is per-product and
we control which id we encode. `segno` new dependency (tiny, well-maintained).
**Acceptance:**
- A fresh scrape of N products yields N rows each with a valid `qr_url` and a
  reachable `qr_image_url`; `qr.svg` opens and decodes to the correct link.
- `tools/backfill_qr.py --region gb-en --dry-run` reports the missing set;
  a live run patches rows without touching other fields (verified by diffing a row).
- `verify_catalog` (if extended) passes.

### Phase 2 — Deep-link hosting (repo `ros-pipeline` / infra; static only)
**Objective:** `<LINK_DOMAIN>` serves the OS verification files and a store-redirect
page — so a scanned link opens the app (installed) or the store (not installed).
**Components:** S3, CloudFront, DNS, ACM.
**Files/artifacts:**
- `infra/link_hosting/apple-app-site-association` (JSON, no extension):
  `{"applinks":{"details":[{"appIDs":["<TeamID>.<bundleId>"],"components":[{"/":"/p/*"}]}]}}`
- `infra/link_hosting/assetlinks.json`: package `com.CitiBIM.IBMROS` + release SHA-256.
- `infra/link_hosting/p/index.html`: static page; JS reads the path's `<canonical_id>`,
  attempts the app deep link, and on failure redirects to App Store / Play Store by
  platform (with a small "Get IBMROS" landing for desktop/unknown).
- CloudFront Function (viewer-request) rewriting `/p/<id>` → `/p/index.html`.
- New `infra/setup_link_hosting.py` (or documented console steps): upload objects
  with correct content-types, create the distribution + alias + cert + function.
**Dependencies:** Phase 0 (domain, cert, Team ID, keystore SHA-256).
**Risks:** AASA must be served **exactly** (HTTPS, correct content-type, no redirect,
reachable at `/.well-known/`), or iOS silently ignores the association — test with
Apple's CDN validator. CloudFront caching can serve a stale AASA — set low TTL
during setup.
**Acceptance:**
- `curl https://<LINK_DOMAIN>/.well-known/apple-app-site-association` returns the JSON
  with `application/json`; Android `assetlinks.json` validates in Google's
  Statement List tester.
- Visiting `https://<LINK_DOMAIN>/p/<known_id>` on a phone **without** the app
  redirects to the correct store; with a debug build installed, opens the app (after Phase 3).

### Phase 4 — Unity: in-app QR scanner (repo `IBMROS Mobile`)
**Objective:** a "Scan" entry in the app opens a camera view, decodes a product QR,
and routes it through the same resolution/navigation as an external scan.
**Recommended library: ZXing.Net** (the C# port of ZXing).
*Why:* pure managed C#, **no native plugins**, works on iOS+Android, decodes QR
from a `WebCamTexture` frame (or an AR Foundation CPU image), mature, Apache-2.0
(commercially safe). Alternatives rejected: per-platform native barcode APIs
(AVFoundation/ML Kit) — better perf but two native codebases to maintain and bridge;
paid Asset Store scanners — unnecessary given ZXing.Net suffices. Perf note: decode
on a background thread and throttle to a few frames/sec to avoid main-thread hitches.
**Components:** UI Toolkit overlay, camera, data layer (reused).
**Files likely to add/change:**
- `Assets/Plugins/ZXing.Net/...` (library) + `Assets/MyStuffs/Scripts/Scanning/QrScannerController.cs`
  (owns `WebCamTexture`/AR camera surface, feeds frames to ZXing, emits decoded string).
- UI Toolkit scanner overlay screen; a **Scan button** added to the Room bottom bar
  (via `RoomUIManager`) and/or the home `MainApp` UXML.
- On decode: hand the string to `DeepLinkManager`'s parser (shared path) →
  `LoadProductByCanonical` → Product Detail screen.
- Camera permission strings (iOS `NSCameraUsageDescription` already written by
  `BuildPostProcessor`; ensure Android `CAMERA` permission).
**Dependencies:** Phase 3 (resolution + detail screen + shared parser).
**Risks:** camera contention with AR Foundation while inside the Room scene —
scanner should pause AR camera use or run in a non-AR context. Frame decode perf on
low-end Android (`minSdk 29`).
**Acceptance:** tapping Scan, pointing at a product QR, opens the correct Product
Detail screen; denying camera permission shows a clear prompt, not a crash.

### Phase 6 — Unity: Add to Current Room + robustness (repo `IBMROS Mobile`)
**Objective:** complete the action set and harden the flow (errors, offline,
duplicates, invalid QR).
**Components:** Room integration, UI, error handling.
**Files likely to change:**
- Product Detail screen ↔ Room: enable **Add to Current Room** only when a Room
  session is active (reuse `ItemDetailSheetController`'s `OnAddToRoomClicked` →
  `FurniturePlacer`/spawn path in the Room scene). If no room open: no auto-create —
  show Save for Later + "Open a room to place this" that routes into room setup (D5).
- **Error handling:**
  - Invalid/foreign QR (not our host/format) → toast "Not an IBMROS product code," no navigation.
  - Unknown/unresolvable id → friendly "Product not available" screen (covers
    discontinued/typo/tampered ids).
  - Network failure during resolve → retry affordance; `NetworkMonitor` already exists.

**Dependencies:** Phases 3–5.
**Risks:** Room-session detection correctness across scene transitions
(`Main` ↔ `Room`); ensure a deep link arriving mid-Room-session doesn't disrupt an
active AR placement.
**Acceptance:** all four actions behave per spec; scanning garbage, an unknown id,
or while offline each produces a defined, non-crashing outcome; rapid repeat scans
don't create duplicates.

## Migration Plan (existing production products)

1. **No re-scrape.** Run `tools/backfill_qr.py --region <r>` per region
   (`gb-en`, `us-en`, `de-de`, `fr-fr`) — idempotent, surgical `update_item`,
   `--dry-run` first, `--limit` for canaries. Mirrors the proven
   `backfill_snapshots.py` migration path.
2. Order: **Phase 1 code merged → backfill dry-run → small `--limit` canary →
   full backfill per region.**
3. Verify with an extended `verify_catalog` (asserts `qr_url` + `qr.svg` presence) and
   spot-check random rows + decode a sample of `qr.svg` files.
4. Hosting (Phase 2) can go live in parallel; links only need to resolve before
   physical tagging (Phase 7), not before backfill.
5. Rollback: `qr_url`/`qr_image_url` are additive optional fields — removing them is
   a `tools/remove_field.py` run; no data loss, no key/GSI change to revert.

## Security Considerations

| Concern | Assessment / Mitigation |
|---|---|
| **QR tampering** | The link carries only a public product id. A tampered id just opens a different (or nonexistent) catalog product — no escalation. Resolver validates against the DB; unknown id → friendly error. |
| **Invalid product ids** | Validate format client-side (host `<LINK_DOMAIN>`, path `/p/`, id = expected article pattern) before querying; unresolved id → "Product not available." |
| **Signed / tokenized links** | **Not needed** (D6). Content is public, read-only, guest-accessible; signing adds key management for no security gain. |
| **Abuse scenarios** | Worst case: someone crafts links to arbitrary product ids or spams scans → app only ever shows read-only catalog products. No writes, no PII. Cognito guest creds + DynamoDB on-demand are already AWS-rate-limited. Client debounces duplicate scans. |
| **Hosting hardening** | Bucket stays private (OAC); CloudFront serves only `/.well-known/*` and `/p/*`; AASA/assetlinks are world-readable *by design* (the OS fetches them). |
| **Auth boundary** | Deep links resolve under **guest** creds (guest-first app); no link can reach an authenticated-only action. Confirm the guest IAM role's `Query` permission is scoped to `ros-products` + `canonical-index` only. |
